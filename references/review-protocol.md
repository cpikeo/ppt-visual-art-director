# 改稿、评审与验收协议

用于**已有 PPTX** 的改稿／评审，以及任何任务的 VERIFY 收尾。十一个评审维度与否决项的定义见 `art-direction.md` §7；门与诊断见 `contract.md` §5–§6。本文件规定**怎么做、怎么看真实成品、怎么定点修正、什么时候停、谁能签、没条件时怎么如实交代**。

## 1. 先判任务模式

| 模式 | 触发 | 产物 | 是否需要 plan |
| --- | --- | --- | --- |
| 新建 | 从内容、大纲或想法做整稿 | 原生 PPTX ＋ 验收报告 | 需要 |
| 改稿 | 给了现有 PPTX，要求调整视觉／结构 | 见 §2 的路线选择 | 视路线而定 |
| 评审 | 要意见、不要改动 | 评审报告（§3），不改文件 | 不需要 |
| 专项 | 只要配色、提示词、某页版式 | 针对性建议；只读相关章节 | 不需要 |

模式不明时按字面最小范围执行，并在开头说明所选模式与假设，不扩大改动。

## 2. 改稿：先解析，再选路线

1. 运行 `python scripts/inspect_pptx.py 原稿.pptx --json inspect.json`，读取画布、母版/版式、每页对象、字体字号、图片 ppi、图表、备注与线索。线索是提示，不是缺陷结论。
2. 列**保留清单**（品牌色、字体、Logo、母版、备注、审定过的文字与数据）与**改动清单**；未被要求改动的内容原样保留。
3. 选路线——**编译器总是生成一份新 PPTX，不在原文件上就地修改**：

| 原稿特征 | 路线 | 说明 |
| --- | --- | --- |
| 以文字／形状／图表／图片为主，无复杂母版 | **整稿重建**：把解析结果写成 plan，重新编译 | 对象变为原生可编辑；逐页对照原稿，确认无内容丢失 |
| 含自定义母版、动画、切换、SmartArt、嵌入对象、宏、批注 | **只给逐页修改指令**，或只重建受影响页并交给用户合并 | 重建会丢失这些特性，须在交付说明中点名；不得声称“完整保留” |
| 仅要求改某几页 | **局部重建 ＋ 清单**：新页单独出文件，标明对应原页码 | 避免波及其余页 |

4. 重建后用 `inspect_pptx.py` 解析新文件，与原稿逐页比对文字、数据、图片数量；不一致必须解释。
5. 原稿事实（数字、来源）不得“顺手修正”；怀疑有误时列入 `open_questions`，交用户确认。

## 3. 评审：只读、可复现、带优先级

输入：PPTX（建议另附渲染图）。步骤：`inspect_pptx.py` → 有渲染工具且能查看图像则按 §4.1 做视觉闭环观察 → 逐页对照 `art-direction.md` §7 的十一个维度。

报告结构（按此顺序，简洁）：

1. **一句话总评**：这套稿最大的问题是什么、值不值得救。
2. **否决项**（语义错误、数据失真、无证因果、关键内容不可读）：逐条给位置、证据、修法；无则写“未发现”，并注明检查范围。
3. **十一个维度**：各给 `PASS / BLOCK / NOT VERIFIED`，并写**实际依据**及其来源——`机器事实`（对象核对、渲染测量、哈希）、`渲染观察`（看过哪一页的 PNG／总览）或 `仅 plan 声明`。没有看过渲染的维度只能是 `NOT VERIFIED`；依据只是“看起来不错”不算依据。
4. **缺陷清单（按严重程度排序）**：每条含位置、观察、根因类别（§4.2）、拟改变量、预期改善。
5. **Top 3 修改**：先写根因，再写改法与预期收益；不堆砌清单。
6. **没检查什么**：渲染环境、目标字体、事实来源、是否能查看图像等。

不打“总分”替代否决项；不因“整体不错”抵消数据失真；不把机器检查的通过率当作审美结论。

## 4. 视觉闭环与根因修正

### 4.1 看真实成品

**前提**：本次 PPTX 已被真实渲染为 PNG（`verify_delivery.py --render-dir` 会写出逐页 PNG 与 `contact_sheet.png`），且当前会话**确实能查看图片**。二者缺一，视觉相关维度一律 `NOT VERIFIED`，不得声称视觉质量已通过。

观察顺序：

1. **缩略总览**：先看整体——是否像同一模板复制、峰值与停顿是否可辨、深浅场切换是否有依据、同一语义的颜色与字族是否一致。
2. **逐页真实 PNG**：每页先问“一眼看到什么”，再对照 plan 的 `focus` 与 `composition_rationale`；检查实际字体与断行、对齐轴、视觉重心、留白连续性、素材最终裁切与文字安静区、图表可读性、页码是否可见。
3. **关键页与相邻页比较**：`open`／`turn`／`close` 页、含图表／图像页，与前后各一页并排看节奏、重量与同构图是否有理由。
4. **分清证据类型**：下表。AI 的设计判断必须写明是判断，不冒充测量。

| 类型 | 例子 | 谁给出 |
| --- | --- | --- |
| 机器能确认的事实 | 对象与 plan 一致、页数页序、图片内嵌哈希、图表实际着色、PDF 词框与溢出、字体是否被替换、对比度数值 | 脚本报告 |
| AI 的设计判断 | 概念是否成立、主次是否按预期被读到、重心是否平衡、断行是否贴合语义、图文是否同族、有无多余元素 | AI 看图后写出，并引用页码与可观察依据 |
| 只能由人确认 | `G-DECK` 整稿设计、`G-TGT` 目标 PowerPoint 环境 | 具名人工（§5） |

5. **按严重程度排序缺陷**：
   - **S1 否决**：语义错误、数据失真、无证因果、关键内容不可读。必须先修，不被其他维度抵消。
   - **S2 阻断主线**：读者读不到主张、层级或重心失效、概念不成立、相邻页节奏断裂。
   - **S3 质量缺陷**：断行、对齐、色彩编码、图形细节、素材裁切。
   - **S4 打磨**：不改变理解的微调；达到停止条件后不再处理。

### 4.2 根因驱动的定点修正

先分类，再改。**上游问题优先**——内容与事实、信息架构、视觉概念一旦变动，下游的构图、排版、色彩修正可能作废，不要先做后者。

| 根因类别 | 典型症状 | 应动的设计变量 | 不要做 |
| --- | --- | --- | --- |
| 内容与事实 | 主张无证据、数据口径冲突、因果被画出来 | `claim`、`evidence`、图表口径、`open_questions` | 用视觉强调掩盖证据缺口 |
| 信息架构 | 重点淹没、顺序与关系不符、重复信息 | 删除重复 → 合并 → 简化 → 重组 → 必要时新增；拆页 | 先加图或装饰 |
| 视觉概念 | 换个行业仍成立、套用行业风格、页间无共同逻辑 | `visual_concept`、图像世界、空间母题、字族角色 | 逐页涂抹风格 |
| 构图与层级 | 不知先看哪里、发空、重心失衡、同构图疲劳 | 尺度、位置、明度、密度、留白、对齐轴、`focus_element` | 给配角一起加粗加色 |
| 字体与排版 | 断行破坏语义、数字与单位拆开、行长失控 | 文案断点（`\n`）、`w`、`font_size` 档位、`runs` | 缩字压行距硬塞 |
| 色彩与图像 | 强调泛滥、深浅切换后前景不对、叠字难读、图与整稿不同族 | 墨阶、语义色、`palette`、`crop_focus`、素材路线 | 以浓遮罩或平均色碰运气 |
| 机器执行 | 对象与 plan 不一致、图表着色漂移、几何越界、字体名未写入 | plan 字段或编译参数；必要时报告脚本缺陷 | 手改 PPTX 让报告变绿 |
| 渲染环境 | 缺字体导致替换、缺渲染工具、LibreOffice 与 PowerPoint 差异 | 不改设计；记录环境，交 `G-PRE` / `G-TGT` | 为适配替代字体而改设计 |

每一次修改都按五步记录（可以只写在回复或 `<项目>/review/` 记录里，不进 plan）：

> **观察到的缺陷** → **根本原因** → **应修改的设计变量** → **预期改善** → **重新渲染后的证据**

约束：

- **一次只动一个因果相关的变量组。** 同时改字号、配色和构图，就无法判断哪一步有效；同一根因下强耦合的几项可视为一组，须说明。
- **局部、可解释、可回退。** 只改出问题的页或元素；改前保留上一版 `plan.json`（或记下旧值）；不推翻已通过的部分。
- **改完必须重新编译、验证并重新渲染**，把前后同一页并排比较，写出“预期改善是否出现”。没出现就回退该改动，重新判断根因，而不是叠加第二个改动。
- 修改不得越过事实边界：不得为让版面成立而改数据、删限定、补来源。

### 4.3 停止原则

满足下列条件即**停止**，如实报告剩余项：

- S1 清零，且没有未处置的 S2；
- 每页的主角能用一句话说出，缩略总览的节奏符合 plan 的 `rhythm`；
- 剩余 S3／S4 已披露，不影响理解与交付；
- 机器门的结论与实际看到的一致（通过不等于好看，失败不等于难看，各自记录）。

出现下列情形也应**停手**：连续两轮修改没有实质改善、在两个方案间来回摇摆、问题实际来自上游（回到 §4.2 的上游类别）或来自渲染环境。此时交给人决策，而不是无意义地反复修改。不以“再优化一轮”替代验收，也不以机器检查通过率作为停止依据。

## 5. AI 预审与人工签收的边界

`G-DECK` 与 `G-TGT` 是**具名人工门**：`reviewer` 必须是真实责任人，`evidence` 是其本机可读的文件，`pptx_sha256` 必须匹配本次文件。

- AI **可以**：看渲染 PNG 与缩略总览，按 §4.1 做**预审**——逐页列出疑点与建议，写入 `<项目>/review/ai-pre-review.md` 之类的记录，作为人工签收的参考。
- AI **不可以**：把自己或“AI 复核”填成人工门的 `reviewer` 并写 `PASS`；替用户声称目标 PowerPoint 已验证；用风险批准替代人工门（`contract.md` §6）。
- 无人可签时：交付状态保持 `BLOCK — Delivery`，并给出**待人工签收清单**（见 §7）。这不是失败，而是如实状态；文件可作为“待验收稿”交付，但不得说“已通过验收”。

**人工签收步骤**：① 计算哈希（Linux `sha256sum 文件.pptx`；macOS `shasum -a 256 文件.pptx`；Windows `Get-FileHash 文件.pptx`）；② 在目标 PowerPoint 逐页查看，截图或记录存入证据文件；③ 新建验收配置 JSON，形状以 `scripts/plan.schema.json` 的 `$defs.acceptanceConfig` 为准（下方为最小骨架，字段名与之逐项对应）；④ 运行 `verify_delivery.py ... --config 验收配置.json`。文件一变，哈希即失效，须重签。

```json
{
  "project": "项目标识",
  "target_powerpoint": {
    "configured": true,
    "version": "目标 PowerPoint 版本",
    "operating_system": "目标操作系统",
    "fonts": ["目标机实际安装的字体"]
  },
  "reviews": {
    "G-DECK": {"status": "PASS", "reviewer": "责任人姓名", "evidence": "review/g-deck.md",
               "pptx_sha256": "本次 PPTX 的 64 位十六进制 SHA-256", "note": "可选说明"},
    "G-TGT":  {"status": "PASS", "reviewer": "责任人姓名", "evidence": "review/g-tgt.md",
               "pptx_sha256": "本次 PPTX 的 64 位十六进制 SHA-256"}
  }
}
```

要点：`status` 取 `PASS` / `BLOCK` / `NOT_VERIFIED`；相对 `evidence` 路径相对于**配置文件所在目录**解析，且文件必须存在；`G-TGT` 另需 `target_powerpoint` 的 `configured`、`version`、`operating_system`、`fonts`。可选字段 `required_gates`、`key_pages`、`high_risk_pages`、`historical_issue_pages`、`sampling`、`risk_approvals` 见 Schema。未写的门保持 `NOT VERIFIED`；任一字段不全，`PASS` 会被降为 `BLOCK`。

## 6. 没有渲染工具（或看不到图像）时

`verify_delivery.py` 在缺少 LibreOffice／poppler 时会如实报告 `G-PRE NOT VERIFIED` 并列出缺失项。此时：

- 仍可完成：编译、`G-STR`、`G-SEM`（含文字对比的声明框估算）、`G-COMPLY`、`inspect_pptx.py`。
- **不得**宣称“已预览／版面无溢出／断行正常”；E013 在无渲染词框时只按声明文本框估算，会披露“未定位字形”。
- 有 PNG 但当前会话无法查看图片时，同样不得做视觉判断；十一个维度中依赖视觉的项记 `NOT VERIFIED`，只汇报机器事实。
- 安装参考（按系统择一，装完重跑）：Debian/Ubuntu `sudo apt install libreoffice-impress poppler-utils fontconfig fonts-noto-cjk`；macOS `brew install --cask libreoffice && brew install poppler`；Windows 可用 winget／choco 安装 LibreOffice 与 poppler 并加入 PATH。Linux 无“微软雅黑”：预览会替换字体，只代表替代字体，目标字体交 `G-TGT`。
- 渲染目录必须为空；重跑请换新目录或先清空。

## 7. 交付说明（最终回复的骨架）

1. **交付物**：文件名、页数、画布；改稿时写明路线与未保留的特性。
2. **设计判断**：整稿概念一句话（由什么洞察推出）、节奏一句话；只写会改变执行的取舍。
3. **门状态表**：`G-STR / G-SEM / G-PRE / G-DECK / G-TGT / G-COMPLY` 各自 `PASS / BLOCK / NOT VERIFIED` 与一句原因；总状态原样引用。
4. **视觉复核**：是否真实渲染并查看了图像；若是，列出看过的范围、发现的缺陷与做过的定点修正（§4.2 五步）；若否，写明 `NOT VERIFIED` 及原因。
5. **待人工签收**：列出需要谁、在什么环境、看什么（`G-DECK`、`G-TGT` 的具体页）。
6. **假设与未决**：占位数据、示例数据、未确认授权的素材、`open_questions`、剩余 S3／S4。
7. **不得出现**：“已通过全部检查”（除非总状态确为 PASS）、对未渲染内容的视觉保证、编造的来源。
