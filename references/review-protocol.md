# 改稿、评审与验收协议

用于**已有 PPTX** 的改稿／评审，以及任何任务的 VERIFY 收尾。设计维度与否决项见 `art-direction.md` §7；门与诊断见 `contract.md` §5–§6。本文件只规定**怎么做、谁能签、没条件时怎么如实交代**。

## 1. 先判任务模式

| 模式 | 触发 | 产物 | 是否需要 plan |
| --- | --- | --- | --- |
| 新建 | 从内容、大纲或想法做整稿 | 原生 PPTX ＋ 验收报告 | 需要 |
| 改稿 | 给了现有 PPTX，要求调整视觉／结构 | 见 §2 的路线选择 | 视路线而定 |
| 评审 | 要意见、不要改动 | 评审报告（§3），不改文件 | 不需要 |
| 专项 | 只要配色、提示词、某页版式 | 针对性建议；只读相关章节 | 不需要 |

模式不明时按字面最小范围执行，并在开头说明所选模式与假设，不扩大改动。

## 2. 改稿：先解析，再选路线

1. 运行 `python scripts/inspect_pptx.py 原稿.pptx --json inspect.json`，读取画布、母版/版式、每页对象、字体字号、图片 ppi、图表、备注与线索。线索是提示，不是缺陷结论。
2. 列**保留清单**（品牌色、字体、Logo、母版、备注、审定过的文字与数据）与**改动清单**；未被要求改动的内容原样保留。
3. 选路线——**编译器总是生成一份新 PPTX，不在原文件上就地修改**：

| 原稿特征 | 路线 | 说明 |
| --- | --- | --- |
| 以文字／形状／图表／图片为主，无复杂母版 | **整稿重建**：把解析结果写成 plan，重新编译 | 对象变为原生可编辑；逐页对照原稿，确认无内容丢失 |
| 含自定义母版、动画、切换、SmartArt、嵌入对象、宏、批注 | **只给逐页修改指令**，或只重建受影响页并交给用户合并 | 重建会丢失这些特性，须在交付说明中点名；不得声称“完整保留” |
| 仅要求改某几页 | **局部重建 ＋ 清单**：新页单独出文件，标明对应原页码 | 避免波及其余页 |

4. 重建后用 `inspect_pptx.py` 解析新文件，与原稿逐页比对文字、数据、图片数量；不一致必须解释。
5. 原稿事实（数字、来源）不得“顺手修正”；怀疑有误时列入 `open_questions`，交用户确认。

## 3. 评审：只读、可复现、带优先级

输入：PPTX（建议另附渲染图）。步骤：`inspect_pptx.py` → 有渲染工具则渲染并看缩略总览 → 逐页对照 `art-direction.md` §7 的八个维度。

报告结构（按此顺序，简洁）：

1. **一句话总评**：这套稿最大的问题是什么、值不值得救。
2. **否决项**（语义错误、数据失真、无证因果、关键内容不可读）：逐条给位置、证据、修法；无则写“未发现”，并注明检查范围。
3. **八个维度**：各给 `PASS / BLOCK / NOT VERIFIED` ＋ 一句依据；没看渲染的维度只能是 `NOT VERIFIED`。
4. **Top 3 修改**：先写根因，再写改法与预期收益；不堆砌清单。
5. **没检查什么**：渲染环境、目标字体、事实来源等。

不打“总分”替代否决项；不因“整体不错”抵消数据失真。

## 4. AI 预审与人工签收的边界

`G-DECK` 与 `G-TGT` 是**具名人工门**：`reviewer` 必须是真实责任人，`evidence` 是其本机可读的文件，`pptx_sha256` 必须匹配本次文件。

- AI **可以**：看渲染 PNG 与缩略总览，做**预审**——逐页列出疑点与建议，写入 `<项目>/review/ai-pre-review.md` 之类的记录，作为人工签收的参考。
- AI **不可以**：把自己或“AI 复核”填成人工门的 `reviewer` 并写 `PASS`；替用户声称目标 PowerPoint 已验证；用风险批准替代人工门（`contract.md` §6）。
- 无人可签时：交付状态保持 `BLOCK — Delivery`，并给出**待人工签收清单**（见 §6）。这不是失败，而是如实状态；文件可作为“待验收稿”交付，但不得说“已通过验收”。
- 人工签收步骤：① 计算哈希（`sha256sum 文件.pptx`；Windows `Get-FileHash 文件.pptx`；macOS `shasum -a 256 文件.pptx`）；② 在目标 PowerPoint 逐页查看，截图存入证据目录；③ 复制 `examples/acceptance.json`，把对应门的 `status` 改为 `PASS`，填写 `reviewer`、`evidence`、`pptx_sha256`，并配置 `target_powerpoint`；④ 重新运行 `verify_delivery.py --config`。文件一变，哈希即失效，须重签。

## 5. 没有渲染工具时

`verify_delivery.py` 在缺少 LibreOffice／poppler 时会如实报告 `G-PRE NOT VERIFIED` 并列出缺失项。此时：

- 仍可完成：编译、`G-STR`、`G-SEM`（含文字对比的声明框估算）、`G-COMPLY`、`inspect_pptx.py`。
- **不得**宣称“已预览／版面无溢出／断行正常”；E013 在无渲染词框时只按声明文本框估算，会披露“未定位字形”。
- 安装参考（按系统择一，装完重跑）：Debian/Ubuntu `sudo apt install libreoffice-impress poppler-utils fontconfig fonts-noto-cjk`；macOS `brew install --cask libreoffice && brew install poppler`；Windows 可用 winget／choco 安装 LibreOffice 与 poppler 并加入 PATH。Linux 无“微软雅黑”：预览会替换字体，只代表替代字体，目标字体交 `G-TGT`。
- 渲染目录必须为空；重跑请换新目录或先清空。

## 6. 交付说明（最终回复的骨架）

1. **交付物**：文件名、页数、画布；改稿时写明路线与未保留的特性。
2. **设计判断**：整稿概念一句话、节奏一句话；只写会改变执行的取舍。
3. **门状态表**：`G-STR / G-SEM / G-PRE / G-DECK / G-TGT / G-COMPLY` 各自 `PASS / BLOCK / NOT VERIFIED` 与一句原因；总状态原样引用。
4. **待人工签收**：列出需要谁、在什么环境、看什么（`G-DECK`、`G-TGT` 的具体页）。
5. **假设与未决**：占位数据、示例数据、未确认授权的素材、`open_questions`。
6. **不得出现**：“已通过全部检查”（除非总状态确为 PASS）、对未渲染内容的视觉保证、编造的来源。
